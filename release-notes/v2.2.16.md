# TankAlarm v2.2.16 — Accurate daily history, consecutive alarm debounce, no duplicate emails, times to the minute

Server, client and viewer release. Pull requests #318 (client alarms), #319 (server daily
history), #320 (duplicate emails) and #321 (times without seconds), merged 2026-09-23.
Details, verification and the review history are in
`CODE REVIEW/CODE_REVIEW_09232026_PRS_318_321_CLAUDE.md`.

## Upgrade order and one manual step

1. **Update the server first, then the clients.** The viewer can be updated at any time.
   - A v2.2.15 server stores history times as doubles, and with 2.2.16 clients' whole-minute
     times one value in 32 would reload up to about 8.5 minutes off.
   - The server trusts on-demand readings only from clients reporting 2.2.16 or later.
     Older clients keep working; their on-demand replies just stay out of history.
2. **Update the email bridge script once** (Google Apps Script users):
   1. Open `/email-setup` on the server and copy the new script.
   2. In your Apps Script project, replace the `SECRET` line and `doPost`. **Set `SECRET`
      back to your own value** (the `?key=` in the EmailRoute URL). Pasted as-is it stays
      `CHANGE-ME`, and every email is then rejected silently. Keep any other functions you
      added, such as the STOP-reply forwarder.
   3. Deploy → Manage deployments → edit → **Version: New version** → Deploy. The `/exec`
      URL stays the same.
   4. Send a test email from the server's Settings page.
3. Optional: raise the EmailRoute timeout in Notehub to 60 s so slow calls are retried less.

## Fixed — daily history (server, S-D03)

- **Monthly history was wiped once a month's file passed 8 KB.** All sensors share one file
  per month and each adds about 122 bytes a day, so a server with 3 or more sensors lost the
  first ~3 weeks of every month. The file is now read row by row at any size, a stored row
  is replaced only by one with more readings, and a file that cannot be read is never
  overwritten: an unparseable file is rebuilt from its readable rows and kept as `.bad`.
- **Days the rollup missed** (server off, or clock not set, at midnight) are rolled up later
  from the readings the server still holds. **Days with no readings stay blank**: nothing is
  interpolated or carried over from another day.
- The history readers (compare, year-over-year, stats, monthly FTP archive) accept month
  files of any size.
- **Archived-client list:** it lost entries once it passed 2 KB; it now keeps up to 48, is
  salvaged entry by entry if unreadable, and History → **Load Data** works for archived
  clients (it answered 400 for every archive).
- **Only real readings enter history:** no reused, faulted or placeholder values (including
  current-loop readings outside 4–20 mA), no guessed times (a reading without a valid
  acquisition time is left out), each reading counted once, voltage only from the same
  measurement, and alarms counted on the day they happened.
- After the upgrade, readings saved by v2.2.15 stay on the charts but are not rolled into
  daily summaries (their freshness cannot be checked), so days already wiped by the 8 KB bug
  are not rebuilt.
- `/api/system-status` has a new `warmTier` block (rollup counters, errors, tick timing).

## Fixed — alarms (client, C-T01)

- **Alarms now need 3 readings in a row.** Previously a normal reading didn't reset the
  count, so three one-off spikes, even days apart, could send a false HIGH or LOW alarm;
  clearing had the same gap. Readings that fail validation are ignored instead of counted.
- **Alarm notes are no longer lost to the rate limiter.** The first 5 minutes after boot no
  longer suppress alarms; an alarm held back by the limits (for example right after a config
  save) is sent later, and only while the reading is still in alarm. Re-sends only publish
  the note; they never switch outputs.
- After a sensor recovers while a level alarm is latched, the alarm is re-sent if the
  reading is still in alarm, so the dashboard no longer shows the tank as clear.
- A relay restored at boot now also sends its alarm note, and every alarm note carries the
  time of the reading it reports.
- Latency is unchanged when readings stay in alarm (3 samples, 60–90 minutes at the default
  30-minute cadence); a level that bounces around a threshold can take extra samples.

## Fixed — duplicate emails (#320)

Notehub retries the email route when the Apps Script bridge takes longer than 30 seconds,
and the bridge sent the email again on every retry, so the morning report sometimes arrived
2–3 times. The bridge now remembers each email (Notehub event ID and a new server message
ID) for 6 hours and skips repeats; a repeat that arrives while the first send is still
running waits for it and sends only if that send failed. See the manual step above.

## Changed — times to the minute (#318, #319, #321)

- Clients send telemetry, daily-report and alarm times as whole minutes (rounded down), so a
  reading can never land on the next day. History keeps one reading per sensor per minute.
- Operator pages no longer show seconds: Transmission Log, History chart tooltips, Server
  Settings, Client Console location time, Email Format preview, the dashboard's update
  countdown, and the viewer's printed report.
- Times shown on pages are written to JSON as whole numbers (a double could be stored up to
  ~8 minutes off). Serial logs, CSV exports, config timestamps, schedules and internal
  timers keep their seconds.

## CI

- New `host-tests` job: hardware-free firmware logic (alarm debounce, the history store, the
  email bridge script) is built and run on every pull request with g++ (ASan/UBSan and -O2)
  and node. `build-firmware` depends on it.

## Known / deferred

- **Relays and float switches are not ready for deployment yet.** The client drives the
  relay LEDs instead of the relay coils and reads inputs I1–I8 from the relay pins (C-A01);
  relay ownership and reset (C-A02) and Clear Relay's sensor identity (S-T01) are also open.
  These are the next project.
- Rare edge cases found in review and left for follow-up: around the ~50-day `millis()`
  wrap, the first alarm of a type could be held for 5 minutes and a long-quiet device could
  keep a stale hourly budget; in a rare three-way retry race the email bridge could send a
  third copy.
- The dashboard's "24 h change" is computed across gaps in data.
- Downgrading to v2.2.15 brings back the 8 KB history loss and the 2 KB archive-list loss for
  existing files.
